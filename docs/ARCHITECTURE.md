# Architecture decision and growth plan

## Current status
The application is a **static, single-user browser MVP**, not a production multi-user system. Its entry point is `index.html`, with externalized CSS in `assets/styles.css`, browser controller/camera integration in `assets/app.js`, and independent domain/validation rules in `assets/scan-domain.js`. Domain tests run in Node without a camera.

The existing `leitor_codigos_mvp_v1` localStorage key and JSON Lines export are retained for compatibility. Moving CSS/JS to external assets **requires serving the entire repository directory**, not just copying `index.html`.

## Data contract
Each scan is an immutable event, with:
- `id`: unique event identifier used for deduplication/idempotent ingestion
- `scanned_at`: client timestamp, UTC ISO 8601 when generated by the app
- `format`: QR/barcode symbology (or `DESCONHECIDO`)
- `value`: **string**, never numeric, preserving leading zeros and Unicode
- `source`: `camera`, `scanner_hid`, `manual` or `importado`
- `movement`: `entrada` or `saida` (optional solely for backward compatibility)

This is version zero of the local export format. **Do not change field meanings**. A production API should use `schema_version: 1` in its transport envelope, keep event IDs stable across retries, and validate at the server independently from the browser.

## Design principles
1. **Domain independent of framework and camera**: parse, validate and deduplicate scan events without using the DOM, `localStorage` or a decoder.
2. **Adapters at boundaries**: camera/USB keyboard adapters emit plain scan text and format; storage adapters persist events; integration adapters send/receive events. UI should not contain database queries.
3. **Append-only semantics**: scanning the same barcode twice may represent two different legitimate movements. Deduplicate transport retries by event `id`, never by `value`.
4. **Explicit failure states**: a failed camera decode must not produce a saved event; a successful read is confirmed only after persistence succeeds.
5. **Backwards-compatible migrations**: preserve and back up historical data before changing storage. Test with old imports and interrupted migrations.
6. **Mobile-first UI**: avoid blocking camera preview with long forms. Use clear success feedback and accessibility labels; do not open URLs encoded in QR payloads automatically.

## Scaling roadmap

### Phase 1: Browser hardening (this branch)
- Separate HTML / CSS / JS; apply baseline CSP; add pure validation module and domain tests.
- Bound file imports and decoded values; preserve existing storage and one-shot scan experience.
- No backend, synchronisation or user roles. This phase improves structure but **does not** make the application scalable in record volume.

### Phase 2: Robust offline-first persistence
- Introduce an async `ScanRepository` abstraction, implemented with IndexedDB, versioned migrations and explicit export/backup.
- Make append atomic and indexed by `id` and `scanned_at`; avoid rewriting all events per scan.
- Keep a bounded in-memory view of recent events; paginate and virtualize history; add storage quota recovery.
- Test restart, storage exhaustion, tab concurrency and crash recovery.

### Phase 3: API and PostgreSQL
- Introduce `POST /api/v1/scans/batch` with schema version, authenticated device/user identity, tenant context, payload limits, deduplication and per-event acknowledgements.
- Backend validates independently; PostgreSQL `scan_events` with unique `id`, indexes by tenant/time/value (as appropriate), `received_at` from server, audit and retention policies.
- Client maintains durable outbox and retries with exponential backoff and idempotent IDs. A scan may be **locally saved** but not yet **synchronised**; distinguish these states clearly.
- Rate limiting, request timeouts, monitoring, backups + restoration drills and load testing are required.

### Phase 4: Extensibility
- Business extensions subscribe to scan events through versioned APIs/webhooks or a message queue, not by reading UI storage.
- Separate product catalog, stock balances and business validations from raw scan events.
- Add permissions and policies per tenant and integration; use integration tests and a compatibility matrix.

## Acceptance gates before production
- Mobile and desktop physical-device tests covering common QR, EAN and Code 128 codes, dim lighting, autofocus, camera switching and external HID scanners.
- Automated tests for schema, import/export round-trip, retries, duplicate events, storage limits and server-side authorization.
- Accessibility audit, dependency/SCA review, browser compatibility testing, performance profiling and vulnerability scanning.
- Secure hosting, logging, incident response, backup restoration and privacy/retention assessment.
